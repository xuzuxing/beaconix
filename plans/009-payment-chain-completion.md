# 009：支付链路补全（迭代 B）

> 2026-10-29，B1–B5 已实现，自动化验证已通过。真实数据库验收按用户要求跳过，真实支付渠道尚未联调。

- 微信 V3、支付宝每次发起支付持久化独立 PaymentAttempt，再调用渠道；商户单号按尝试生成。Payment 保留一次业务结算，记录获胜商户单号供退款使用。
- 每五分钟查询未终态尝试，使用带令牌和截止时间的数据库租约；回调与查单共用金额核对、订单准入和组织 / 订单锁。瞬时查询失败保留重试，渠道终态失败才写 FAILED。
- 保留旧 Order.orderNo 回调与退款兼容，迁移回填旧支付尝试。不同尝试重复付款只记录资金事实和异常，不重复开通订阅。
- 用户取消、管理员取消和到期取消共用关单流程；先查单并尝试渠道关单，失败记录并继续本地取消，后续轮询重试。渠道调用不占用数据库事务。
- 微信退款回调核对退款金额、原单金额和支付渠道；退款、查询使用最终结算商户单号。
- 测试覆盖独立尝试、创建失败 / 取消竞态、旧回调、金额不符、回调与查单幂等、多渠道重复付款、租约、关单重试和退款核对；补离线 HTTP 全链集成验证。
- 已运行 Prisma 生成 / validate / 离线迁移检查、类型检查、lint、单测、构建与独立复核。真实渠道联调和 PostgreSQL 迁移 / 并发测试不计作完成。

## 最终实现与验证

- B1/B2：V3、支付宝共用支付扫描；认证查单与验签回调共用金额校验及结算入口。每次查询领取 120 秒尝试租约；在组织 / 订单 / 尝试行锁内验证租约后消费结果，关单结果与清理均校验 token 和截止时间。
- B3：用户、管理员、过期取消共用先查单后关单的路径。关单失败本地仍取消，保留 closePending / lastError 重试；query→close 之间付款时再次查单补结算。支付宝未建交易不能视为已关单。新发起支付调用渠道期间被取消时，不向客户端返回可支付参数。
- B4：先持久化独立尝试，再发渠道请求。回调早于创建响应、创建超时后查单、不同渠道双付均保持一单一次权益结算。取消/退款后的到账记 PAID 并通知人工退款。虚拟支付也补锁内二次准入、晚到付款记录；虚拟退款按获胜 Payment 身份定位，不按最新 PAID 任取。
- B5：微信退款回调必须携带且匹配退款/原单金额；可选币种/商户号/渠道交易号同时核对，不匹配不修改业务状态。统一退款与查询使用获胜商户号，保留历史回退。
- 新增 53 个单测：支付有状态夹具 17、退款身份 10、调度 2、虚拟边界 7、渠道适配与客户端 17；全量单测为 **176 suites / 2400 tests**。
- `test/billing-payment.e2e-spec.ts` **3/3**：真实 controller / JWT 与租户 guards / DTO 验证 / service，内存持久化和模拟渠道；覆盖下单→回调或查单→订阅→退款→对账，以及鉴权与退款金额拒绝。
- Prisma client 生成、schema validate、离线 schema diff、类型检查、lint、build 已执行。离线 diff 的表结构与迁移 DDL 一致；旧支付数据回填 SQL 只做静态复核，没有在真实库执行。
- 独立只读复核发现的退款误选尝试、支付宝 NOT_EXIST 误判、虚拟支付取消竞态、租约过期写入均已修复，最终复核未发现新的可确认 P1/P2。
- 前端文档：`docs/api/payment-reconciliation.md`；设计记录：`docs/design/billing.md` 的顶部说明。

## 保留的验证边界与上线顺序

- 内存事务夹具串行化并支持回滚，能验证状态转移/幂等，不能证明真实 PostgreSQL 的行锁行为或性能。
- 未执行真实库迁移、并发测试或真实微信/支付宝调用。
- 上线应先暂停旧版本的支付写入并停止旧支付进程，备份后由部署流程执行新增迁移与历史回填，再启用新版本（本轮没有执行这些操作）。旧进程不得在回填之后继续新增无 attempt 的支付记录。
- 五分钟是扫描周期；每批 100 条，有积压或渠道故障时不承诺五分钟内结算。未终态与关单失败会持续重试；异常付款仅通知人工核查退款，不自动对第二笔付款执行退款。
