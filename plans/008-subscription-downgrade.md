# 008：套餐降级后的监控数量限制与邮件通知

> 状态：后端实现与回归已完成；新增迁移尚未应用到数据库。日期：2026-10-28。
> 上游：006 的商业化体验工作，以及 007 后续业务讨论。

## 1. 已确认的范围

- 套餐实际降级后，数量超额的监控有 **72 小时宽限期**；宽限结束后按新套餐限制运行。
- 保留监控配置和历史数据。
- **发送邮件通知**，并复用现有站内通知与投递机制。
- 本轮宽限规则针对监控数量超额；高级监控类型、检测频率、租户探针等能力的降级规则另行讨论。

实现采用以下默认规则：组织 OWNER / ADMIN 可选择保留运行的监控；未指定或名额未填满时，按创建时间升序、ID 升序稳定补齐前 N 个。手动暂停的配置仍占名额，与现有数量配额一致；项目软删除不改变监控配置计数。

## 2. 现有代码基线

- `SubscriptionExpiryService` 已有到期前 7 / 3 / 1 天以及到期通知，事件使用 `email: true`，不需要另建同类邮件任务。
- 现有收件人为订单购买者与组织 OWNER / ADMIN；新增降级通知建议沿用，按用户去重。
- `NotificationsService.publish(event, tx)` 已支持事务内通知记录与持久化投递，使用 `eventKey` 去重。
- `QuotaService.monitorEligibility` 已限制监控类型与间隔，数量超额尚不影响已有监控运行。
- 现有 `maxMonitors` 按未删除的监控计数，暂停监控仍占数量；本方案需要明确区分配置数量和运行名单。

## 3. 数量限制的实施口径

1. 按订阅栈计算实际生效套餐变化。某条订阅过期但生效套餐未降级，或者新套餐仍容纳全部监控时，不启动超额宽限。
2. 宽限起点取实际降级的生效时间，截止时间为起点 + 72 小时；任务延迟、重启和重复扫描不延长宽限。
3. 宽限期内保持已有监控运行，同时提供超额数量、运行名额、宽限截止时间与保留名单。新增和恢复仍受当前套餐的既有数量校验约束。
4. 截止时重新检查当前有效套餐和资源数量，按当时权限与配额执行。用户已经续费、减少资源或不再超额时，不执行过期的限制任务。
5. 套餐限制独立于用户手动暂停记录，不直接覆盖 `enabled`。被限制的监控不调度、不接受绕过限制的手工执行，也不把政策停执行当作服务故障发送告警；状态展示必须说明停止观测，不能把历史 UP 当作实时健康。
6. 续费后重新计算可运行范围，只解除系统套餐限制，不恢复用户手动暂停的监控。
7. 同一组织的套餐变化、保留名单变更与限制执行需要协调组织行锁；本地检查和探针结果处理使用一致的运行准入口径。

## 4. 邮件通知

| 时机 | 邮件内容 | 与已有能力的关系 |
|---|---|---|
| 到期前 7 / 3 / 1 天 | 套餐到期时间、可能降级的影响、续费入口 | 复用既有到期提醒；只有确实存在降级影响才描述对应后果 |
| 实际降级且进入超额宽限 | 原/新套餐、当前数量与可运行数量、72 小时截止时间、选择保留监控及续费入口 | 扩充既有到期邮件或合并成同一事件，避免同时发两封到期邮件 |
| 宽限剩余不超过 24 小时 | 精确截止时间、预计停止数量、处理入口 | 每个降级周期一次；已解除超额则不发 |
| 数量限制实际执行后 | 实际停止数量、保留运行数量、受影响监控查看入口、恢复方式 | 与限制结果同事务记录，不能在尚未停止时声称已停止 |
| 续费解除限制后 | 已解除限制的数量及仍手动暂停的说明 | 优先合并到既有支付/订阅激活通知，避免重复发送 |

建议收件人沿用组织 OWNER / ADMIN 与订单购买者；投递时复用现有通知权限检查，避免向已失去组织访问权的用户泄露资源信息。

- 邮件由通知投递链路异步发送，失败复用现有重试机制，不阻塞订阅或监控事务。
- 幂等键包含组织、持久化降级周期 ID、通知阶段和收件人；不要用每次扫描的当前时间生成新键。
- 扫描发现多个提醒阶段已过期时，仅发送仍有行动价值的阶段，避免系统停机后集中补发过时提醒。
- 时间展示带明确时区；元数据保留标准时间值，前端和邮件按站点约定格式展示。
- 内容提供可访问的处理入口，不在邮件中嵌入监控凭据、目标 URL 中的敏感信息等。

## 5. 实施顺序与验收

1. 细化降级周期持久化、运行名单和 API 契约，明确与配置数量配额的关系。
2. 实现宽限起止、运行准入与续费解除，并接入本地/探针执行链路。
3. 扩充通知事件与邮件内容，接入既有 outbox、去重和重试机制。
4. 回归覆盖：重复扫描不延长宽限；72 小时边界；指定/默认保留名单稳定；到期后续费或删减资源；再次降级产生新周期；手动暂停不被恢复；邮件收件人去重与权限校验；多实例只生成一次阶段通知；邮件失败不回滚业务；限制与恢复邮件中的数量符合实际。

## 6. 已落地实现

- 持久化 `MonitorCapacityCycle`、组织观察游标及 `Monitor.quotaGraceEndsAt`。每个组织最多一个开放周期；关闭周期作为幂等记录保留。批量更新运行限制，不修改 `enabled`。
- 按订阅开始 / 到期边界重放停机期间的套餐变化，覆盖首尾套餐相同、连续降级和冻结套餐恢复。不同批次保留各自截止时间；重复扫描不重新计时。
- 本地调度、队列执行、手动检查、探针心跳、原始结果入库 / 重放、状态写入与告警投递接入数量限制；状态详情、概览、insights、dashboard 和公开状态页将受限监控视为 UNKNOWN。
- 解除已生效限制时提升 revision / configRevision，等待新的观测；手动暂停保持暂停。软删除监控恢复时在配额事务内清除旧限制。
- 每分钟执行容量核对和系统探针分配刷新；保留名单变更不会延长宽限。运行入口也核对当前套餐与截止，不依赖定时任务准点执行。
- 到期前 7 / 3 / 1 天邮件增加到期时间、可能的数量影响和管理入口。新增进入宽限、各截止批次最后 24 小时、限制生效与解除事件，复用站内通知和邮件 outbox；避免重复发送泛用到期邮件。
- 邮件投递重新核对角色、周期状态摘要、截止时间与已恢复监控的当前限制，跳过被后续操作覆盖的结论。邮件失败沿用异步重试，不影响已提交业务。
- 恢复邮件采用独立容量事件，适用于支付、人工结算和调整保留名单等来源，没有与付款成功邮件合并。处理入口使用 `app.webUrl` 并附组织参数；本仓库没有前端计费页面。

### API（OWNER / ADMIN）

- `GET /api/organizations/:orgId/subscription/monitor-capacity`
- `PATCH /api/organizations/:orgId/subscription/monitor-capacity`

PATCH 请求示例：

```json
{"cycleId":"<当前周期 CUID>","monitorIds":["<优先保留的监控 CUID>"]}
```

返回数据包含 `cycleId`、`status`（WITHIN_LIMIT / GRACE / LIMITED）、`startsAt`、`graceEndsAt`、`limit`、`total`、`overLimit`、`excess`、`selectedMonitorIds`、`retainedMonitorIds`、`restrictedMonitorIds` 及 `monitorDeadlines`。后者包含每个排除监控的 ID、独立截止时间和 enabled，供连续降级时展示不同批次。空选择采用默认保留顺序。过期周期、重复 / 外组织 / 不可用 ID 和超出名额的选择返回 400；服务在事务中再次检查权限。
