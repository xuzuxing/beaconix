# 系统总体设计

## 设计目标与设计原则

本系统的设计目标是在单套部署实例内支撑多个组织的数据隔离与独立运营，同时保证监控检查这一高并发、长耗时、易失败的环节不会拖累对外接口的响应能力。围绕该目标，系统遵循以下设计原则。

- **租户隔离优先**。任何业务查询都必须携带组织或项目边界，租户标识由请求路径与父级资源推导后二次校验，跨租户访问在服务层即被阻断。
- **权限最小化**。接口默认要求认证，公开访问必须显式声明；组织级与项目级权限分别判定，角色按等级下限匹配，不做隐式放大。
- **主链路轻量化**。接口服务只做参数校验、权限判定与数据读写，耗时操作（监控检查、告警推送、邮件发送、批量清理）一律投递队列或由定时任务承担。
- **状态外置**。接口服务不保存会话状态，令牌自包含，队列与缓存外置到 Redis，服务实例可随时增删。
- **失败可恢复**。删除采用软删除，外部投递失败保留记录并可重试，异步任务具备幂等性，异常不吞没、不导致主流程回滚。
- **变更可追溯**。所有写操作经统一审计入口记录变更前后快照，敏感字段脱敏落库，审计与业务解耦。
- **契约即文档**。接口元数据以装饰器声明，文档在运行时生成，避免文档与实现脱节。

## 总体架构

本系统采用分层架构，自上而下分为接入层、应用层、领域模块层、基础设施层与外部集成层。

表 3-1 系统分层结构

| 层次 | 组成 | 职责 |
| --- | --- | --- |
| 接入层 | 反向代理、HTTPS 终结、静态资源 | 承载外部流量，统一入口与证书管理 |
| 应用层 | 全局中间件、参数校验、认证守卫、授权守卫、响应包装、异常过滤 | 请求进入业务逻辑前的统一处理与出口规范化 |
| 领域模块层 | 账号、组织、协作、监控、告警、探针、运营、开放能力等业务模块 | 业务规则实现与数据读写编排 |
| 基础设施层 | 数据库、缓存与队列、日志、观测、对象存储、定时调度 | 提供持久化、异步执行与可观测能力 |
| 外部集成层 | 邮件服务、即时通讯平台、微信开放能力、支付平台 | 与第三方系统交互 |

系统在部署上支持三种形态：单机部署（应用、数据库、缓存部署于同一主机，适用于测试与验证）、分离部署（应用服务器与数据库、缓存服务器独立，适用于生产环境）、容器编排部署（通过镜像与编排文件一键启动，适用于弹性伸缩场景）。三种形态使用同一份代码与同一套环境变量，差异仅在基础设施地址与容量配置。

领域模块层按能力域进一步划分，各模块之间通过服务接口调用，不跨模块直接访问对方的数据表；共享能力（数据库访问、缓存、日志、鉴权判定）下沉到公共层。这种组织方式使监控域可以在不依赖协作域内部实现的前提下复用组织与成员体系。

## 请求处理流程

所有业务请求按固定顺序经过以下处理环节，任一环节判定失败即中断并返回统一错误响应。

1. **安全响应头**。为每个响应附加内容安全策略、XSS 防护、帧嵌入限制等安全头，并放行接口文档页面所需的静态资源来源。
2. **跨域处理**。按配置的来源白名单处理跨域预检与凭证传递，未配置白名单时不放行跨域请求。
3. **参数校验与转换**。按接口声明的数据结构校验请求，剔除未声明字段，完成类型转换与默认值填充，校验失败返回参数错误。
4. **访问频率限制**。按接口与来源统计访问频率，超限返回限流错误，验证码、登录、找回密码等敏感接口采用更严格的阈值。
5. **身份认证**。校验访问令牌的有效性与时效，解析用户身份并挂载到请求上下文；标记为公开的接口跳过该环节。
6. **租户与权限判定**。从路径参数或父级资源推导组织标识，校验用户在该组织中的成员资格与角色等级；项目级资源额外校验项目成员与资源授权。
7. **业务处理**。控制器完成参数绑定后调用领域服务，领域服务执行规则校验与数据读写，必要时投递队列任务。
8. **响应包装**。将业务返回值统一包装为包含数据主体与元信息（含时间戳）的结构，敏感字段在序列化阶段剔除。
9. **异常归一化**。业务异常、参数异常、认证异常、未知异常统一转换为标准错误结构，未知异常不向外暴露堆栈细节。

审计环节以拦截器形式挂在业务处理之后：写操作在进入业务前抓取变更前快照，在响应返回后抓取变更后快照，异步落库，审计失败不影响主流程。

### 核心关系

- 组织是数据的根节点：成员、邀请、项目、标签、规则组、探针、通知渠道、状态页、审计日志、订阅与订单均直接归属组织。
- 用户与组织之间通过成员实体建立多对多关系，成员携带角色，是权限判定的依据。
- 项目归属组织，迭代归属项目，任务归属项目并可归入某个迭代；任务可设置父任务形成层级，可通过依赖实体建立阻塞关系，可通过关注实体建立订阅关系。
- 评论、附件、标签均以任务或项目为宿主，通过外键级联约束保证一致性。
- 监控目标归属项目，其当前状态以一对一关系独立存储，检查结果以多对多之外的独立实体按时间追加，形成可查询的历史序列。
- 规则组归属组织，通过规则绑定与监控目标建立多对多关系；告警事件由监控目标与规则共同产生，每一次对外通知形成一条投递记录。
- 探针归属组织（租户探针）或归属平台（系统探针），通过监控探针关联实体与监控目标建立多对多关系。
- 订阅与订单归属组织，订单与支付一对多关联，支付成功的订单驱动订阅状态变更。

### 关键设计说明

- **软删除**。组织、项目、任务、评论等实体设置删除时间字段，删除仅打标记，查询默认过滤已删除数据；配合恢复接口与定期清理任务，兼顾误删恢复与容量控制。
- **状态与历史分离**。监控当前状态独立存放以支撑高频读取，历史数据按时间追加并设置保留策略，避免单一热表无限膨胀。
- **快照式审计**。审计日志保存操作前后的完整快照而非字段差异，便于还原任意时刻的数据形态；口令、令牌类字段在写入前脱敏。
- **枚举集中管理**。角色、任务状态与优先级、监控类型与状态、执行状态、通知渠道、订单与支付状态、工单状态等取值以枚举统一定义，接口层与数据层共用同一套取值，避免字面量散落。
- **组织维度唯一约束**。项目标识键、状态页访问标识等需要对外唯一的字段，约束范围限定在组织内，既保证组织内不重复，又允许不同组织使用相同标识。
- **级联与限制并用**。强从属关系（如任务与评论）采用级联删除；弱引用关系（如任务与标签）采用关联表并在解除时仅删除关联记录。

## 接口规范

### 路径与版本

全部业务接口挂载在 `/api` 前缀下，开放接口挂载在 `/developer/v1` 前缀下。资源路径遵循层级表达，如组织下的项目为 `/api/organizations/{orgId}/projects`，项目下的监控为 `/api/projects/{projectId}/monitors`。路径中的层级参数同时承担租户边界判定职责。

### 认证方式

系统支持两种凭据：面向终端用户的访问令牌，以 `Authorization: Bearer <token>` 形式传递；面向组织集成方的组织凭据，以同一请求头承载 API Key。两种凭据由不同的守卫识别并将身份信息挂载到请求上下文，业务代码不感知凭据类型差异。

访问令牌具有时效，过期后使用刷新令牌换取新令牌；刷新采用轮换策略，旧刷新令牌在换发后立即失效，泄露的旧令牌无法再次使用。

### 响应结构

成功响应统一包装为数据主体加元信息两部分，元信息包含服务端时间戳。列表类接口在数据主体中返回条目集合与分页信息，分页支持页码与每页条数参数，每页条数设有上限。

失败响应统一包含错误标识、错误说明与可选的字段级细节，参数校验失败时逐字段返回不通过的约束，便于调用方定位。

表 3-4 常用响应状态

| 状态 | 含义 | 典型场景 |
| --- | --- | --- |
| 200 | 成功 | 查询、更新操作完成 |
| 201 | 已创建 | 资源创建成功 |
| 204 | 无内容 | 删除成功或无需返回数据 |
| 400 | 请求参数错误 | 字段缺失、类型不符、约束不满足 |
| 401 | 未认证 | 令牌缺失、过期或无效 |
| 403 | 无权限 | 非组织成员、角色等级不足、资源越权 |
| 404 | 资源不存在 | 标识不存在或已被删除 |
| 409 | 状态冲突 | 唯一键冲突、状态机不允许的流转 |
| 429 | 请求过频 | 触发访问频率限制 |
| 500 | 服务内部错误 | 未预期异常，响应不包含堆栈 |

### 分页、排序与筛选

列表接口统一支持分页参数，支持按创建时间或业务字段排序，支持按状态、关键字、时间区间等条件筛选。筛选参数在接口层完成枚举值与类型校验，非法取值直接返回参数错误，不下发到数据层。

### 接口文档

系统在运行时依据接口元数据生成 OpenAPI 描述文档，并在 `/api/docs` 提供可交互的调试界面，支持访问令牌与组织凭据两种认证方式在线调试。文档随代码同步更新，不需要单独维护。
