# 可靠性与运维

本章说明系统的后台任务、异步处理、可观测性、健康检查、部署方式与数据维护策略。

## 定时任务

系统将周期性作业以调度队列方式统一注册，每个作业有固定名称与执行周期，支持失败重试与执行记录，避免在多实例部署时重复执行。

表 11-1 定时任务清单

| 任务名称 | 执行周期 | 作用 |
| --- | --- | --- |
| 邀请过期处理 | 每小时 | 将超过有效期的邀请置为已过期，并通知邀请人与受邀人 |
| 任务临期提醒 | 每日 | 扫描即将到达截止时间的未完成任务，提醒指派人与关注者 |
| 任务逾期提醒 | 每日 | 扫描已超过截止时间仍未完成的任务，提醒责任人与关注者 |
| 令牌清理 | 每日 | 清理已过期或已吊销且超过保留期的刷新令牌记录 |
| 附件清理 | 每日 | 清理已删除附件的存储文件与失去关联的孤儿文件 |
| 监控数据清理 | 每日 | 按保留策略清理过期的检查明细与历史聚合数据 |
| 订阅到期处理 | 每小时 | 处理临期提醒、到期降级与暂停订阅的自动恢复 |
| 订单超时关闭 | 每小时 | 关闭超过支付有效期仍未支付的订单 |

定时任务的设计约束：任务内部处理幂等，同一作业重复执行不产生重复数据；单次执行按批处理，避免一次性加载大量数据；任务执行耗时与结果写入服务日志，可在管理后台查看调度队列的积压与失败情况。

## 队列与异步处理

系统使用消息队列承载三类异步工作。

表 11-2 队列划分

| 队列 | 生产者 | 消费者 | 说明 |
| --- | --- | --- | --- |
| 监控扫描队列 | 调度器 | 扫描工作进程 | 周期性找出到期监控并派发检查任务 |
| 监控检查队列 | 扫描工作进程、接口服务 | 检查工作进程 | 执行具体检查并写入结果 |
| 通知投递队列 | 告警模块、通知模块 | 投递工作进程 | 发送外部通知与告警消息 |
| 定时任务队列 | 调度注册器 | 作业工作进程 | 执行周期性作业 |

异步化的收益与代价：接口响应不被慢操作阻塞，检查与投递可独立扩容；代价是需要处理重复消费与失败重试。系统通过以下方式保证正确性：检查任务按监控与时间窗口去重，重复消费不会产生重复检查记录；投递任务以投递记录标识去重，重复消费不会重复发送；失败任务按退避策略重试，超过重试次数后标记失败并保留记录。

队列积压是重要的运维信号。管理后台的调度指标接口返回各队列的等待数、处理中数量与失败数量，超过阈值时应增加工作进程或排查下游依赖。

## 日志与可观测性

### 日志

系统输出结构化日志，包含时间、级别、请求标识、方法、路径、状态码、耗时与操作者标识。日志按级别分流：错误日志记录异常堆栈与上下文，警告日志记录可恢复的异常情况（如投递失败、检查超时），普通日志记录请求摘要。

敏感信息不入日志：口令、令牌、凭据、渠道密钥在日志输出前脱敏；请求体仅在调试模式下按白名单记录，且默认关闭。

### 指标

系统暴露运行指标，包含请求量、响应时间分布、错误率、队列积压、检查执行量与告警投递成功率。指标以标准格式暴露，可被监控采集系统抓取。系统自身的可用性同样可由本系统监控，形成自监控闭环。

### 追踪

每个请求携带唯一标识，该标识在日志、审计记录与异步任务中传递，便于从一条告警或一次失败反查到完整链路。

## 健康检查

系统提供三个健康检查接口，供编排系统与负载均衡使用。

表 11-3 健康检查接口

| 接口 | 用途 | 检查内容 |
| --- | --- | --- |
| 综合健康检查 | 人工与运维巡检 | 汇总各依赖状态，返回整体结论 |
| 存活检查 | 容器编排的存活探针 | 仅检查进程是否可响应，不检查依赖 |
| 就绪检查 | 容器编排的就绪探针 | 检查数据库与缓存的连通性，未就绪时不接收流量 |

存活检查与就绪检查分离的意义：数据库短暂不可用时，进程本身健康，不应被重启；但此时不应接收新流量，因此就绪检查失败而存活检查通过，编排系统会将实例摘除而不重启，避免雪崩式重启。

## 部署与配置

### 环境变量

系统通过环境变量注入配置，按用途分为应用配置、数据库配置、缓存配置、认证配置、存储配置、邮件配置、第三方平台配置与限流配置。全部必填项在启动时校验，缺失或格式错误时启动失败并输出明确的缺失项，避免以不完整配置运行。

表 11-4 主要配置分组

| 分组 | 主要配置项 |
| --- | --- |
| 应用 | 运行环境、监听端口、跨域来源白名单、公开访问地址 |
| 数据库 | 连接地址、库名、账号、口令、连接池参数 |
| 缓存与队列 | 连接地址、口令、库序号、队列并发数 |
| 认证 | 令牌签名密钥、访问令牌有效期、刷新令牌有效期 |
| 存储 | 存储方式、本地目录、对象存储地址与凭据、公开访问前缀 |
| 邮件 | 服务商凭据、发件人、模板标识 |
| 第三方平台 | 微信应用标识与密钥、支付商户配置、即时通讯密钥 |
| 限流 | 时间窗口、常规阈值、敏感接口阈值 |

### 容器化部署

系统提供多阶段构建的镜像定义，构建阶段完成依赖安装与编译，运行阶段仅保留产物与运行依赖，镜像体积与攻击面同时收敛。编排文件可一键启动应用、数据库与缓存三个服务，适用于本地验证与单机部署。

部署步骤：

1. 准备环境变量文件，填写数据库、缓存、认证密钥与第三方平台配置。
2. 执行数据库迁移，创建或升级表结构。
3. 启动应用，确认健康检查接口返回就绪。
4. 执行初始化脚本创建首个平台管理员账号。
5. 通过接口文档页面验证接口可用。

### 升级与回滚

升级时先执行数据库迁移再启动新版本；迁移脚本向前兼容，保证旧版本实例在滚动升级期间仍可运行。回滚时回退镜像版本，已执行的迁移不回退（迁移设计为可兼容旧代码）。发布窗口内可开启维护模式，避免升级过程中产生写入冲突。

### 优雅停机

进程收到终止信号后停止接收新请求，等待处理中的请求完成，并将队列中的未完成任务交还队列，随后关闭数据库与缓存连接。该机制保证实例缩容或滚动发布时不会丢失处理中的请求与任务。

## 数据维护

- **软删除数据的清理**。软删除记录在保留期内可由用户恢复；超过保留期后由清理任务物理删除，同时清理关联数据。
- **历史数据保留**。检查明细、聚合历史与审计日志各自设置保留周期，周期可按容量与合规要求调整。
- **附件清理**。已删除附件的存储文件与失去关联的孤儿文件由定时任务清理，避免存储无限增长。
- **备份建议**。数据库应配置定期全量备份与增量备份，附件存储应开启版本或跨区备份；备份恢复演练建议按季度执行。
- **容量评估**。检查明细是增长最快的表，容量评估应结合监控数量、检查周期与保留周期共同计算，必要时缩短明细保留期并延长聚合数据保留期。
